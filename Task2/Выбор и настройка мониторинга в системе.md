# Выбор и настройка мониторинга в системе

## Мотивация

### Бизнес-контекст
Компания «Александрит» переживает период активного роста: каждый месяц количество заказов увеличивается на 100, а во втором квартале был запущен API для партнеров, что привело к резкому росту нагрузки. Одновременно с этим участились жалобы клиентов на просроченные заказы и потеря крупных B2B контрактов.

### Проблемы, которые решает мониторинг

**1. Реактивный подход к проблемам**
- Сейчас о проблемах узнаем от клиентов через жалобы
- Нет понимания, когда и где происходят сбои
- Время реакции на инциденты критически высокое

**2. Отсутствие visibility в производительности**
- Не видим узкие места в архитектуре
- Нет данных для принятия решений об оптимизации
- Невозможно планировать масштабирование

**3. Невозможность SLA контроля**
- Нет метрик для отслеживания выполнения обещаний клиентам
- Сложно оценить реальное качество сервиса
- Нет инструментов для улучшения customer experience

### Ценность для бизнеса

**Снижение рисков:**
- Предотвращение потери клиентов через proactive мониторинг
- Сокращение времени восстановления с часов до минут
- Защита репутации через контроль качества сервиса

**Экономические выгоды:**
- Сокращение operational costs через раннее выявление проблем
- Оптимизация ресурсов на основе реальных данных использования
- Увеличение conversion rate через улучшение производительности

**Конкурентные преимущества:**
- Возможность гарантировать SLA партнерам
- Данные для принятия стратегических решений о развитии
- Основа для автоматизации и self-healing систем


## Выбор подхода к мониторингу

### Архитектурный анализ системы

Система «Александрит» представляет собой распределенную архитектуру с тремя основными компонентами:
- **Frontend-сервисы** (Online Shop, CRM, MES) - взаимодействие с пользователями
- **Integration layer** (RabbitMQ) - асинхронная интеграция
- **Data layer** (PostgreSQL, S3 storage) - хранение данных

### Стратегия мониторинга по компонентам

**1. User-facing сервисы (Online Shop, CRM, MES UI)**
- **Подход:** RED (Rate, Errors, Duration)
- **Обоснование:** Эти сервисы напрямую влияют на user experience. Критично отслеживать скорость ответа, количество ошибок и throughput.

**2. Backend API (CRM API, MES API, Shop API)**
- **Подход:** Четыре золотых сигнала (Latency, Traffic, Errors, Saturation)
- **Обоснование:** API требуют комплексного мониторинга, включая saturation для предотвращения перегрузок.

**3. Infrastructure компоненты (RabbitMQ, Databases)**
- **Подход:** USE (Utilization, Saturation, Errors)
- **Обоснование:** Для инфраструктурных компонентов критично понимать утилизацию ресурсов и точки насыщения.

**4. Business процессы (Order lifecycle)**
- **Подход:** Business metrics + SLI/SLO
- **Обоснование:** Необходимо отслеживать ключевые бизнес-процессы для контроля выполнения обещаний клиентам.

## Метрики системы

### 1. Frontend/UI Метрики (RED подход)

**Page Load Time**
- **Зачем:** Напрямую влияет на conversion rate и user satisfaction
- **Ярлыки:** 
  - `page` (main, product, checkout, dashboard)
  - `user_type` (customer, seller, operator, admin)
  - `device` (desktop, mobile, tablet)
- **Threshold:** p95 < 3s для критичных страниц

**User Session Duration**
- **Зачем:** Индикатор engagement и usability проблем
- **Ярлыки:**
  - `application` (shop, crm, mes)
  - `user_role` (customer, manager, operator)
- **Benchmark:** Среднее время сессии операторов должно расти (больше заказов в работе)

**Error Rate по страницам**
- **Зачем:** Выявление проблемных участков UI
- **Ярлыки:**
  - `page`, `error_type` (js_error, api_error, timeout)
  - `user_agent`, `browser`

### 2. API Метрики (Четыре золотых сигнала)

**Request Rate (Traffic)**
- **Зачем:** Понимание нагрузки и capacity planning
- **Ярлыки:**
  - `endpoint` (/api/orders, /api/price-calculation, /api/files)
  - `method` (GET, POST, PUT, DELETE)
  - `source` (web, mobile, api_partner)
  - `user_type` (authenticated, anonymous, api_user)

**Request Duration/Latency**
- **Зачем:** Контроль производительности API, особенно критично для price calculation
- **Ярлыки:**
  - `endpoint`, `method`
  - `calculation_complexity` (simple, medium, complex) - для price calculation
  - `file_size_range` (<1MB, 1-10MB, >10MB) - для file uploads

**Error Rate**
- **Зачем:** Мониторинг качества сервиса и stability
- **Ярлыки:**
  - `endpoint`, `status_code`
  - `error_category` (client_error, server_error, timeout, validation)
  - `source` - для выявления проблемных клиентов/интеграций

**Resource Saturation**
- **Зачем:** Предотвращение перегрузок и планирование масштабирования
- **Ярлыки:**
  - `resource` (cpu, memory, connections, queue_depth)
  - `service` (shop-api, crm-api, mes-api)

### 3. Infrastructure Метрики (USE подход)

**CPU Utilization**
- **Зачем:** Мониторинг загрузки для масштабирования и performance troubleshooting
- **Ярлыки:**
  - `instance` (shop-01, crm-01, mes-01)
  - `service`, `environment` (dev, release, prod)

**Memory Utilization**
- **Зачем:** Предотвращение OOM и оптимизация allocation
- **Ярлыки:**
  - `instance`, `service`
  - `memory_type` (heap, non_heap, buffer) - для JVM приложений

**Disk I/O**
- **Зачем:** Выявление bottlenecks в storage, особенно критично для 3D файлов
- **Ярлыки:**
  - `instance`, `mount_point`
  - `operation` (read, write)

**Network I/O**
- **Зачем:** Мониторинг bandwidth и network latency между сервисами
- **Ярлыки:**
  - `instance`, `interface`
  - `direction` (in, out)

### 4. Database Метрики

**Connection Pool Usage**
- **Зачем:** Предотвращение connection exhaustion
- **Ярлыки:**
  - `database` (shop_db, crm_db, mes_db)
  - `pool_type` (read, write)

**Query Duration**
- **Зачем:** Выявление медленных запросов, влияющих на UX
- **Ярлыки:**
  - `database`, `operation` (select, insert, update, delete)
  - `table` (orders, users, files)
  - `query_type` (dashboard, search, crud)

**Database Size**
- **Зачем:** Планирование storage и архивации
- **Ярлыки:**
  - `database`, `table`

### 5. Message Queue Метрики (RabbitMQ)

**Queue Depth**
- **Зачем:** Критично для выявления bottlenecks в order processing
- **Ярлыки:**
  - `queue` (price_calculation, order_updates, notifications)
  - `priority` (high, normal, low)

**Message Processing Time**
- **Зачем:** Мониторинг performance обработки сообщений
- **Ярлыки:**
  - `queue`, `message_type` (price_request, status_update)

**Consumer Lag**
- **Зачем:** Выявление проблем с обработкой сообщений
- **Ярлыки:**
  - `consumer`, `queue`

### 6. Business Метрики

**Order Processing Time по статусам**
- **Зачем:** Контроль выполнения SLA по срокам изготовления
- **Ярлыки:**
  - `status_from` → `status_to` (SUBMITTED → PRICE_CALCULATED)
  - `complexity` (simple, medium, complex)
  - `source` (web, api)
  - `priority` (rush, normal)

**Price Calculation Success Rate**
- **Зачем:** Критичная бизнес-операция, влияющая на conversion
- **Ярлыки:**
  - `complexity`, `file_format` (stl, obj, 3mf)
  - `calculation_duration_range` (<5min, 5-15min, >15min)

**Revenue per Hour**
- **Зачем:** Бизнес-импакт downtime и performance проблем
- **Ярлыки:**
  - `source` (direct, api), `product_type` (standard, custom)

**Customer Satisfaction Score (через API feedback)**
- **Зачем:** Прямой индикатор качества сервиса
- **Ярлыки:**
  - `customer_type` (b2c, b2b), `order_complexity`

### 7. Дополнительные специфичные метрики

**File Upload Success Rate**
- **Зачем:** 3D модели критичны для бизнеса, проблемы с upload блокируют заказы
- **Ярлыки:**
  - `file_size_range`, `file_format`
  - `upload_source` (web, mobile, api)

**3D Model Processing Time**
- **Зачем:** Оптимизация pipeline обработки моделей
- **Ярлыки:**
  - `polygon_count_range` (<1k, 1k-10k, 10k-100k, >100k)
  - `processing_step` (validation, optimization, cost_calculation)

**API Rate Limiting Hits**
- **Зачем:** Мониторинг usage patterns партнеров и capacity planning
- **Ярлыки:**
  - `api_key`, `endpoint`
  - `limit_type` (requests_per_minute, requests_per_hour)

**Cache Hit/Miss Rate**
- **Зачем:** Оптимизация performance через кэширование
- **Ярлыки:**
  - `cache_type` (price_cache, model_cache, user_session)
  - `service`

## Алертинг стратегия

### Критичные алерты (немедленная реакция)
- Error rate > 5% за 5 минут
- API latency p95 > 10s
- Queue depth > 1000 сообщений
- Price calculation failure rate > 10%

### Предупреждающие алерты (в течение часа)
- CPU > 80% за 15 минут
- Memory > 90% за 10 минут
- Order processing time превышает SLA на 50%

### Информационные алерты (daily/weekly reports)
- Trends в business метриках
- Capacity планирование метрики
- Performance regression анализ

## Показатели насыщенности и действия при превышении

### 1. CPU Utilization

**Пороговые значения:**
- Warning: 70% в течение 10 минут
- Critical: 85% в течение 5 минут
- Emergency: 95% в течение 2 минут

**Обоснование:** При 70% утилизации начинается деградация performance, при 85% - заметное влияние на response time, при 95% - риск полной недоступности сервиса.

**Действия при превышении:**
- **70%:** Автоматическое создание тикета для анализа, уведомление DevOps команды в Slack
- **85%:** Немедленное уведомление on-call инженера, автоматический scale-out (если настроен)
- **95%:** Критический алерт с звонком on-call инженеру, эскалация до тимлида через 10 минут

### 2. Memory Utilization

**Пороговые значения:**
- Warning: 80% heap memory для JVM приложений
- Critical: 90% heap memory
- Emergency: 95% heap memory + GC pressure

**Обоснование:** JVM начинает частые GC циклы при заполнении heap > 80%, что влияет на latency. При 95% высок риск OutOfMemoryError.

**Действия при превышении:**
- **80%:** Мониторинг GC метрик, создание тикета для memory profiling
- **90%:** Уведомление on-call, подготовка к restart сервиса
- **95%:** Автоматический graceful restart сервиса, немедленная эскалация

### 3. Database Connection Pool

**Пороговые значения:**
- Warning: 70% активных соединений
- Critical: 85% активных соединений
- Emergency: 95% активных соединений

**Обоснование:** При исчерпании connection pool новые запросы будут получать timeout, что критично для всех операций.

**Действия при превышении:**
- **70%:** Анализ slow queries, создание тикета для оптимизации
- **85%:** Увеличение размера pool (если возможно), уведомление DBA
- **95%:** Критический алерт, возможное временное отключение неприоритетных функций

### 4. RabbitMQ Queue Depth

**Пороговые значения:**
- Warning: 1000 сообщений в очереди price_calculation
- Critical: 5000 сообщений в любой очереди
- Emergency: 10000 сообщений (риск memory overflow)

**Обоснование:** Накопление сообщений указывает на bottleneck в обработке. Для price_calculation это критично, так как влияет на customer experience.

**Действия при превышении:**
- **1000:** Анализ consumer performance, уведомление команды
- **5000:** Масштабирование consumers, приоритизация обработки
- **10000:** Критический алерт, возможная остановка producers для стабилизации

### 5. API Response Time (p95)

**Пороговые значения:**
- Warning: p95 > 2 секунды для критических API
- Critical: p95 > 5 секунд
- Emergency: p95 > 10 секунд или timeout rate > 5%

**Обоснование:** Response time напрямую влияет на user experience и conversion rate. При > 10 секунд пользователи начинают покидать сайт.

**Действия при превышении:**
- **2s:** Анализ slow queries и bottlenecks, performance profiling
- **5s:** Уведомление product команды, возможное включение circuit breaker
- **10s:** Критический алерт, анализ возможности temporary disable неприоритетных функций

### 6. Disk Space

**Пороговые значения:**
- Warning: 80% заполнения диска
- Critical: 90% заполнения
- Emergency: 95% заполнения

**Обоснование:** При заполнении диска > 95% PostgreSQL может перестать принимать записи, что критично для системы.

**Действия при превышении:**
- **80%:** Планирование очистки логов и временных файлов
- **90%:** Немедленная очистка, архивация старых данных
- **95%:** Критический алерт, возможное увеличение размера диска

### 7. Error Rate

**Пороговые значения:**
- Warning: 2% ошибок за 5 минут
- Critical: 5% ошибок за 5 минут
- Emergency: 10% ошибок или полная недоступность сервиса

**Обоснование:** Error rate > 5% указывает на серьезные проблемы в системе, влияющие на customer satisfaction.

**Действия при превышении:**
- **2%:** Анализ логов ошибок, создание тикета
- **5%:** Уведомление on-call, анализ возможности rollback
- **10%:** Критический алерт, немедленный rollback или отключение проблемной функциональности

### Автоматизация ответных действий

**Уровень 1 - Автоматические действия:**
- Auto-scaling при превышении CPU/Memory thresholds
- Автоматическая очистка логов при заполнении диска
- Circuit breaker activation при высоком error rate

**Уровень 2 - Полуавтоматические действия:**
- Предложение restart сервиса через Slack bot
- Автоматическое создание incident tickets
- Подготовка rollback команд для quick execution

**Уровень 3 - Ручные действия:**
- Анализ root cause
- Координация с бизнес командой
- Долгосрочное планирование решений

Такой подход позволит быстро получить visibility в систему и начать proactive управление качеством сервиса с четкими SLA и автоматизированными ответами на проблемы.
