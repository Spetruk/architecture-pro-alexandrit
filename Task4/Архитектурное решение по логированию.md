# Архитектурное решение по логированию для компании «Александрит»

### Список логов уровня INFO для сбора

#### Онлайн-магазин:
- **Создание заказа**: время, user_id, order_id, статус (INITIATED)
- **Загрузка файла 3D-модели**: время, user_id, order_id, размер файла, формат, статус (FILE_UPLOADED)
- **Отправка заказа**: время, user_id, order_id, статус (SUBMITTED)
- **Запросы к API**: время, endpoint, method, response_time, status_code, user_id
- **Аутентификация**: время, user_id, action (login/logout), IP-адрес, user_agent

#### CRM:
- **Подтверждение заказа**: время, manager_id, order_id, статус (MANUFACTURING_APPROVED)
- **Закрытие заказа**: время, manager_id, order_id, статус (CLOSED)
- **Работа с клиентами**: время, manager_id, customer_id, action_type
- **Обработка сообщений RabbitMQ**: время, queue_name, message_id, processing_result

#### MES:
- **Расчёт стоимости**: время, order_id, calculation_time, polygon_count, price, статус (PRICE_CALCULATED)
- **Начало производства**: время, operator_id, order_id, статус (MANUFACTURING_STARTED)
- **Завершение производства**: время, operator_id, order_id, статус (MANUFACTURING_COMPLETED)
- **Упаковка**: время, operator_id, order_id, статус (PACKAGING)
- **Отправка**: время, operator_id, order_id, shipping_company, статус (SHIPPED)
- **API-запросы от внешних клиентов**: время, client_id, endpoint, response_time, status_code

#### RabbitMQ:
- **Сообщения в очереди**: время, source_system, target_system, message_type, order_id, processing_status

### Дополнительные уровни логирования

- **WARN**: Медленные запросы (>1 сек), повторные попытки обработки, переполнение очередей RabbitMQ
- **ERROR**: Ошибки расчёта стоимости, недоступность внешних сервисов, ошибки валидации файлов
- **DEBUG**: Детальная информация для разработки (только в dev-окружении)

## Мотивация

### Зачем нужно логирование
Компания испытывает критические проблемы с отслеживанием заказов и жалобами клиентов. Сейчас для разбора проблем требуется много времени, поскольку анализ происходит только со слов клиентов. Логирование позволит:

1. **Быстро выявлять узкие места** в процессе обработки заказов
2. **Проактивно обнаруживать проблемы** до жалоб клиентов
3. **Автоматизировать мониторинг** критических процессов
4. **Снизить нагрузку на поддержку** за счёт самодиагностики

### Технические метрики решения
1. **Время разрешения инцидентов**: сократится с 4-6 часов до 30-60 минут
2. **Время выявления проблем**: с реактивного (после жалоб) на проактивное (в реальном времени)
3. **Доступность системы**: повышение с текущих ~95% до 99%+
4. **Производительность расследований**: ускорение в 5-10 раз

### Бизнес-метрики решения
1. **Удовлетворённость клиентов**: снижение жалоб на 60-70%
2. **Время обработки заказов**: оптимизация процессов на 20-30%
3. **Потери от простоев**: сокращение на 80%+
4. **Эффективность команды поддержки**: высвобождение 40% времени для развития продукта

### Приоритизация внедрения
**Первая очередь (критично)**:
1. **MES** - расчёт стоимости и производственные процессы (больше всего жалоб)
2. **RabbitMQ** - интеграционные процессы между системами
3. **Онлайн-магазин API** - внешние клиенты (риск потери контрактов)

**Вторая очередь**:
4. **CRM** - внутренние процессы управления
5. **Пользовательские интерфейсы** - клиентские взаимодействия

## Предлагаемое решение

### Архитектура логирования

[Обновленная Диаграмма C#](jewerly_c4_model.drawio)

FYI: В микросервисах: CRM, MES, Shop-API добавил Filebeat, указать припиской на схеме в каждом "+Filebeat"

### Технологический стек
- **Filebeat**: сбор логов с каждого сервера
- **Logstash**: обработка и обогащение логов
- **Elasticsearch**: хранение и индексирование
- **Kibana**: визуализация и дашборды

### Компоненты для внедрения

#### 1. Filebeat на каждом сервере
- Мониторинг лог-файлов приложений
- Отправка в Logstash для обработки
- Обработка ротации логов

#### 2. Logstash (централизованный)
- Парсинг логов разных форматов
- Обогащение данными (геолокация, пользовательская информация)
- Фильтрация и маршрутизация по индексам

#### 3. Elasticsearch кластер
- Отдельные индексы для каждой системы
- Настройка маппингов для оптимального поиска
- Политики ротации данных

#### 4. Kibana
- Дашборды для мониторинга заказов
- Поиск по логам для техподдержки
- Визуализация метрик производительности

### Политика безопасности

#### Обработка чувствительных данных
- **Исключение из логов**: пароли, токены аутентификации, полные номера карт
- **Маскирование**: частичное скрытие персональных данных (email: `u***@example.com`)
- **Хеширование**: user_id заменяется на необратимый хеш для анонимизации

#### Контроль доступа
- **Разработчики**: полный доступ к техническим логам (без персональных данных)
- **Поддержка**: доступ к логам заказов и пользовательским действиям
- **Менеджеры**: доступ только к агрегированным метрикам и дашбордам
- **Аудит**: все действия в системе логирования протоколируются

### Политика хранения

#### Структура индексов
- `alexandrite-shop-{YYYY.MM.DD}` - логи онлайн-магазина
- `alexandrite-crm-{YYYY.MM.DD}` - логи CRM
- `alexandrite-mes-{YYYY.MM.DD}` - логи MES
- `alexandrite-rabbitmq-{YYYY.MM.DD}` - логи очередей

#### Сроки хранения
- **Критичные логи** (заказы, платежи): 2 года
- **Операционные логи**: 6 месяцев
- **Debug логи**: 30 дней
- **Метрики производительности**: 1 год

#### Объёмы данных
- Ожидаемый объём: ~50GB в месяц при текущей нагрузке
- Прогноз на год: ~600GB с учётом роста
- Резерв на масштабирование: +100%

## Система анализа логов

### Алертинг
**Критичные алерты** (немедленно в Slack + email):
- Ошибки расчёта стоимости в MES
- Недоступность RabbitMQ >1 минуты
- Рост времени ответа API >5 секунд
- Переполнение очередей сообщений

**Предупреждения** (email):
- Медленные запросы >3 секунд
- Необычный рост нагрузки (+50% от базовой)
- Ошибки загрузки файлов >10% от общего количества

### Детекция аномалий
**Автоматические проверки**:
- **Резкий рост запросов**: если RPS вырос в 3+ раза за 5 минут
- **Массовые ошибки**: если error rate >5% в течение 2 минут
- **Застрявшие заказы**: если заказ не меняет статус >24 часов
- **Подозрительная активность API**: необычные паттерны вызовов

**Машинное обучение** (будущее развитие):
- Предсказание узких мест на основе исторических данных
- Автоматическое выявление новых типов проблем
- Корреляционный анализ между метриками разных систем

### Обоснование выбора ELK

**Преимущества ELK для компании «Александрит»**:

1. **Открытый исходный код**: возможность модификации под специфические нужды
2. **Богатая экосистема**: множество готовых интеграций для Java/Spring Boot и C#/.NET
3. **Активное сообщество**: быстрое решение проблем и постоянное развитие
4. **Гибкость**: легко адаптируется под различные форматы логов наших систем
5. **Готовые дашборды**: для мониторинга веб-приложений и API

**Почему не выбираем альтернативы**:
- **OpenSearch**: меньше готовых решений, менее зрелая экосистема
- **Splunk**: слишком дорого для растущей компании
- **Самописные решения**: требуют больших инвестиций в разработку

ELK обеспечивает оптимальный баланс функциональности, стоимости и простоты внедрения для текущих потребностей компании.
