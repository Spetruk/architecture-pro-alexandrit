# Архитектурное решение по трейсингу

## Анализ системы в контексте трейсинга

### Идентификация критических точек для трейсинга

**Анализ C4-диаграммы выявил следующие системы, требующие покрытия трейсингом:**

1. **Online Shop (Container: Vue, TypeScript, Threejs)**
   - Критические точки: создание заказа, загрузка 3D файлов, отправка заказа
   - Риски: потеря данных при сбоях браузера, некорректная загрузка файлов

2. **Shop API (Container: SpringBoot)**
   - Критические точки: валидация заказов, сохранение в БД, отправка в очередь
   - Риски: ошибки валидации, сбои при записи в БД, потеря сообщений в RabbitMQ

3. **Messages Queue (Container: RabbitMQ)**
   - Критические точки: доставка сообщений между системами
   - Риски: потеря сообщений, dead letter queue, дублирование

4. **MES API (Container: C#)**
   - Критические точки: расчет стоимости, обновление статусов заказов
   - Риски: зависание расчетов, ошибки в алгоритмах расчета, потеря результатов

5. **CRM API (Container: SpringBoot)**
   - Критические точки: подтверждение заказов, обновление статусов
   - Риски: рассинхронизация статусов, потеря уведомлений клиентам

6. **CRM (Container: Vue, TypeScript)**
   - Критические точки: действия менеджеров, изменение статусов
   - Риски: человеческие ошибки, потеря контекста заказа

7. **MES (Container: React, TypeScript)**
   - Критические точки: взятие заказов в работу, обновление производственных статусов
   - Риски: потеря информации о производстве, некорректные обновления

### Список данных для трейсинга

**Контекстная информация заказа:**
- `order_id` - уникальный идентификатор заказа
- `customer_id` - идентификатор клиента
- `order_source` - источник заказа (web, mobile, api)
- `api_key` - для API заказов от партнеров
- `session_id` - идентификатор пользовательской сессии

**Технические данные:**
- `trace_id` - уникальный идентификатор трейса
- `span_id` - идентификатор текущего span
- `parent_span_id` - идентификатор родительского span
- `service_name` - название сервиса
- `operation_name` - название операции
- `timestamp` - время начала и окончания операции
- `duration` - длительность операции

**Бизнес-данные:**
- `order_status` - текущий статус заказа
- `previous_status` - предыдущий статус
- `file_id` - идентификатор загруженного 3D файла
- `file_size` - размер файла
- `complexity_level` - уровень сложности изделия
- `price_calculation_result` - результат расчета стоимости
- `operator_id` - идентификатор оператора (для MES)
- `manager_id` - идентификатор менеджера (для CRM)

**Данные об ошибках:**
- `error_code` - код ошибки
- `error_message` - сообщение об ошибке
- `stack_trace` - стек вызовов (в dev/staging)
- `retry_count` - количество попыток повтора

**Метаданные интеграций:**
- `queue_name` - название очереди RabbitMQ
- `message_id` - идентификатор сообщения
- `correlation_id` - идентификатор корреляции
- `routing_key` - ключ маршрутизации

## Мотивация

### Бизнес-проблемы, решаемые трейсингом

**1. Потеря заказов и недовольство клиентов**
- Сейчас команда не может быстро найти "потерянные" заказы
- Клиенты жалуются на просроченные заказы без понимания причин
- Потеря крупных B2B контрактов из-за проблем с отслеживанием

**2. Неэффективность service desk**
- Менеджеры тратят часы на поиск информации о заказах
- Нет понимания, на каком этапе "застрял" заказ
- Ручное расследование каждого инцидента

**3. Техническая деградация**
- Команда разработки не может быстро локализовать проблемы
- Нет понимания, какие интеграции работают нестабильно
- Долгое время восстановления после инцидентов

### Техническая ценность трейсинга

**1. Быстрая диагностика проблем**
- Сокращение времени поиска проблем с часов до минут
- Автоматическое выявление bottlenecks в процессах
- Visibility в распределенные транзакции

**2. Проактивное выявление проблем**
- Мониторинг аномалий в процессах обработки заказов
- Раннее предупреждение о деградации performance
- Автоматическое выявление паттернов ошибок

**3. Оптимизация процессов**
- Данные для оптимизации алгоритмов расчета стоимости
- Выявление неэффективных path в обработке заказов
- Основа для автоматизации и self-healing

### Метрики, на которые повлияет внедрение трейсинга

**Технические метрики:**

1. **Mean Time To Resolution (MTTR)**
   - Текущее состояние: 4-8 часов на расследование проблемы
   - Ожидаемое улучшение: сокращение до 15-30 минут
   - Измерение: время от получения жалобы до локализации проблемы

2. **Order Processing Success Rate**
   - Текущее состояние: неизвестно (нет visibility)
   - Ожидаемый результат: > 99.5% успешных обработок
   - Измерение: процент заказов, прошедших все этапы без ошибок

3. **API Integration Reliability**
   - Текущее состояние: частые жалобы на потерю сообщений
   - Ожидаемое улучшение: < 0.1% потерянных сообщений
   - Измерение: процент успешно доставленных сообщений между сервисами

**Бизнес-метрики:**

4. **Customer Satisfaction Score**
   - Текущее состояние: снижение из-за просроченных заказов
   - Ожидаемое улучшение: рост на 20% за счет прозрачности процесса
   - Измерение: NPS score и количество жалоб на поддержку

5. **Operational Efficiency**
   - Текущее состояние: 30% времени команды тратится на troubleshooting
   - Ожидаемое улучшение: сокращение до 10%
   - Измерение: время команды, потраченное на расследование инцидентов

## Предлагаемое решение

### Архитектура трейсинга

**Выбор технологического стека:**

1. **OpenTelemetry** - стандарт для instrumentation
   - Поддержка Java (Spring Boot), .NET, JavaScript
   - Vendor-agnostic решение
   - Богатая экосистема библиотек

2. **Jaeger** - система сбора и анализа трейсов
   - Open source решение
   - Хорошая производительность и масштабируемость
   - Web UI для анализа трейсов

3. **Elasticsearch** - хранение трейсов
   - Быстрый поиск по трейсам
   - Интеграция с существующей инфраструктурой
   - Возможность аналитики

### Компоненты решения

**1. Instrumentation библиотеки**
- **Spring Boot сервисы:** OpenTelemetry Java SDK + Spring Boot starter
- **.NET сервис (MES):** OpenTelemetry .NET SDK
- **Frontend приложения:** OpenTelemetry JavaScript SDK
- **RabbitMQ:** кастомные headers для propagation trace context

**2. Collection и Processing**
- **Jaeger Collector** - сбор spans от всех сервисов
- **Jaeger Agent** - локальные агенты на каждом сервере
- **Elasticsearch** - долгосрочное хранение трейсов

**3. UI и Analytics**
- **Jaeger UI** - интерфейс для анализа трейсов
- **Grafana dashboards** - аналитика по трейсам

### Интеграция с существующими системами

**1. Modification существующих сервисов:**
- Добавление OpenTelemetry dependencies
- Конфигурация trace exporters
- Инструментация критических методов
- Propagation trace context через HTTP headers

**2. RabbitMQ интеграция:**
- Добавление trace headers в messages
- Custom middleware для propagation
- Correlation ID mapping для асинхронных операций

**3. Database интеграция:**
- Инструментация database queries
- Корреляция с business operations
- Анализ database performance в контексте заказов

### Схема обновленной архитектуры

**Новые компоненты трейсинга (красным цветом):**
- **Jaeger Collector** - сбор и обработка трейсов от всех сервисов
- **Jaeger UI** - веб-интерфейс для просмотра и анализа трейсов
- **Trace Storage (Elasticsearch)** - хранение данных трейсов
- **OpenTelemetry instrumentations** - библиотеки в каждом сервисе
- **RabbitMQ trace propagation** - передача trace context через headers

### Автоматический мониторинг и алертинг (дополнительное задание)

**1. Order Journey Monitoring (без ML)**
- **Rule-based order tracking** - отслеживание заказов по временным правилам
- **SLA violation detection** - простые проверки превышения времени обработки
- **Stuck order detection** - если заказ не меняет статус > 2 часов для расчета, > 24 часа для производства
- **Status transition validation** - проверка корректности переходов между статусами

**2. Integration Health Monitoring**
- **Message delivery success rate** - мониторинг доставки сообщений RabbitMQ
- **Service availability checks** - health checks каждые 30 секунд
- **Response time monitoring** - алерты при latency > 5 секунд
- **Error rate tracking** - алерты при error rate > 5%

**3. Simple Alerting система:**
- **Prometheus + AlertManager** для сбора метрик и алертов
- **Webhook integration** с Slack/email для уведомлений
- **Simple escalation** - повторный алерт через 15 минут если проблема не решена
- **Business hours routing** - разная логика алертов в рабочее и нерабочее время

**Компоненты автоматического мониторинга (зеленым цветом):**
- **Order Status Monitor** - простой сервис отслеживания статусов заказов
- **Health Check Service** - проверка доступности всех сервисов
- **Alert Manager** - централизованная система алертов
- **Metrics Collector** - сбор метрик из трейсов
- **Business Dashboard** - простой дашборд для бизнеса

## Компромиссы

### Ограничения текущей реализации

**1. Проприетарные системы**
- **Ограничение:** Нет доступа к исходному коду MES (купленный софт)
- **Компромисс:** Трейсинг только на уровне API calls, без внутренней логики
- **Митигация:** Дополнительное логирование на границах системы

**2. Legacy код и технический долг**
- **Ограничение:** Части кода могут быть сложны для инструментации
- **Компромисс:** Поэтапное внедрение, начиная с критических path
- **Стоимость:** 2-3 недели дополнительной разработки на рефакторинг

**3. Performance overhead**
- **Ограничение:** Трейсинг добавляет 2-5% overhead на latency
- **Компромисс:** Sampling rate 10% в production для снижения нагрузки
- **Митигация:** Adaptive sampling на основе важности операций

**4. Дорогостоящие интеграции**
- **Ограничение:** Полная инструментация 3D processing pipeline
- **Компромисс:** Трейсинг только входных/выходных точек
- **Стоимость:** Полная инструментация потребует 1-2 месяца разработки

**5. Data privacy и sensitive information**
- **Ограничение:** Customer data не должна попадать в трейсы
- **Компромисс:** Только технические идентификаторы, без personal data
- **Митигация:** Data sanitization middleware

### Случаи, когда трейсинг не принесет пользы

**1. Внутренние операции MES**
- Купленная система с закрытым кодом
- Нет возможности добавить custom instrumentation
- Можно отслеживать только входы/выходы

**2. Frontend пользовательские действия**
- Приватность: нельзя трейсить действия конечных пользователей
- Ограниченная польза для B2B debugging
- Высокий объем данных с низкой ценностью

**3. Производственные операции**
- Физические процессы изготовления украшений
- Нет технической возможности интеграции с IT системами
- Ручные процессы операторов

## Аспекты безопасности

### Внутренняя безопасность

**1. Аутентификация и авторизация**
- **Требование:** Доступ к Jaeger UI только для сотрудников компании
- **Реализация:** Интеграция с корпоративным LDAP/Active Directory
- **Роли:** 
  - `tracing:read` - разработчики, QA, DevOps
  - `tracing:admin` - архитекторы, тимлиды
  - `support:read` - служба поддержки (ограниченный доступ)

**2. Data sanitization**
- **Требование:** Исключение персональных данных из трейсов
- **Контроль:** Регулярные аудиты данных в трейсах

**3. Сетевая изоляция**
- **Требование:** Jaeger компоненты в изолированной сети
- **Мониторинг:** Логирование всех подключений к tracing системе

### Внешняя безопасность

**1. API партнеров**
- **Ограничение:** Трейсы API партнеров не должны содержать их sensitive data
- **Реализация:** Хеширование API keys в трейсах
- **Политика:** Согласование с партнерами объема собираемых данных

**2. Data retention**
- **Политика:** Хранение трейсов не более 30 дней в production
- **Реализация:** Автоматическое удаление старых данных
- **Исключения:** Критические инциденты - до 90 дней для расследования

**3. Compliance**
- **GDPR:** Трейсы не содержат personalmente identifiable information
- **Аудит:** Логирование доступа к sensitive traces
- **Encryption:** TLS для всех коммуникаций, encryption at rest для Elasticsearch

### Защита от несанкционированного доступа

**1. Network security**
- **Firewalls:** Ограничение доступа к Jaeger портам
- **TLS:** Обязательное шифрование всех connections

**2. Application security**
- **Rate limiting:** Защита от DDoS на Jaeger endpoints
- **Input validation:** Валидация всех trace данных
- **Security headers:** OWASP recommended headers

**3. Operational security**
- **Monitoring:** Алерты при подозрительной активности
- **Backup:** Регулярные backup критических конфигураций
- **Incident response:** План реагирования на security инциденты

Данное архитектурное решение обеспечивает comprehensive visibility в order lifecycle при соблюдении безопасности и privacy требований, с возможностью поэтапного внедрения и минимизации рисков.
